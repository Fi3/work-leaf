# Buildable work-unit mechanism experiment

Status: prospective design; no observations are admitted by this document alone. Admission requires
the completed implementation, required checks, real subscription verification, a separately drawn
allocation, and a frozen `PHASE-MANIFEST.json`. The original `screen-01` protocol, helpers, records,
and no-candidate decision remain immutable. This is a different hypothesis, not a rerun of either
unsuccessful one-sentence screen.

## Question and experimental factor

Does WL's cohesive-patch/ready-for-review policy reduce the number of accepted work-unit handoffs
and subsequent model continuations, compared with allowing naturally separable, independently
buildable increments of the same requested work?

The two conditions are `control` and `buildable-work-unit-incremental`, using the same feature-enabled
binary and v2 instrumentation. `DESIGN-BUILDABLE-WORK-UNIT.md` specifies the three exact renderer-owned
treatment spans: the shared work-unit instruction, each already-selected test-instruction translation,
and the successful acknowledgment's permission to continue remaining requested work. These are one
semantic policy, not separately estimable sentence effects. Only their declared bytes may differ.

No minimum patch count, per-file split, artificial task, extra tool call, failing intermediate shared
tree, or redundant validation is prescribed. The normal at-most-one focused validation instruction,
required tests, ownership enforcement, command results, read representation, review, linearization,
and final checks remain identical. All current non-linearizer policy injection roles retain their
existing scope. The public policy renderer remains baseline; private benchmark delivery owns the
intervention. A default build excludes the experiment.

The semantic task is the original three-feature workflow at base
`c92a0b7060a36eac6db2d869b85e589a7a9480f9`, task-list SHA-256
`45bee25a4b929182d36612fc5a159597e7770f25dba9c95760713a401d45598a`.
All generation uses the existing ChatGPT subscription, CLI 0.153.4, GPT-5.5, and `xhigh`; no API-key

## Fixed allocation and retention

The proposed phase contains exactly twelve fresh whole workflows: six control and six treatment.
Two blocks each contain six launch slots in two waves of three. In each block, independently draw
uniformly from the eighteen allocations with three labels of each condition and both labels in each
wave. This gives 324 possible joint allocations. Record the draw before provider admission with a
create-new claim; never redraw after an allocation is obtained. Three complete workflows execute
concurrently, in separate checkouts and artifact directories. Launch order is separately randomized
within each wave.

Do not inspect interim treatment comparisons to stop, extend, substitute, or select favorable
observations. Infrastructure integrity failure withholds subsequent admissions while active runs
reach their bounded recorded outcomes. Every admitted identity, failed attempt, missing measurement,
and withheld workflow remains in the report. An incomplete fixed phase is not a completed
randomization test. No confirmation observations are pooled with exploratory `screen-01` observations.

The primary directional test receives alpha 0.025. This phase consumes at most that allocation of a
0.05 family-wise budget for confirmatory mechanism claims in the continuation of this investigation.
Any further confirmatory mechanism test requires a prospective allocation from the remaining budget;
an unsuccessful phase does not refund alpha. Diagnostic and exploratory reports do not receive
confirmatory labels. There is no data-dependent sample-size extension.

## Primary mediator and mechanistic validation

The primary outcome is the whole-workflow count of **actually delivered successful patch
acknowledgments**. Delivery requires a unique accepted actual `turn/start` carrying the exact
renderer-owned acknowledgment and matching typed RPC reply, thread and turn identities. The frozen
source emits this boundary for an aggregated successful patch-application group; the driver does not
publish a separate typed `PatchApplied` event log. Do not invent exact commit-to-ACK joins from
transcript ordering. A written trace, duplicate notification, rejected request, or
queued-but-unsent prompt is not delivery. Identical text accepted in two distinct turns counts twice;
a later generation failure does not erase an accepted delivery. A genuine successful-ACK prompt after
an accepted replay/no-op counts in the primary and remains separately classified; the distinct
`work-leaf patch already applied` continuation is not this boundary. Count one acknowledgment prompt, not individual changed files,
provisional commits, trace spans, cumulative notifications, or `done` episodes. A response can contain
multiple edits that WL aggregates into one acknowledgment. Conversely, the treatment can continue
several genuine work units before one `done`; counting only completed ACK-to-done episodes would miss
that mediator. Count all stages and failures within the admitted scope; do not discard costly repairs.

Use the mean treatment-minus-control count and the exact one-sided randomization p-value over the
324 allowed allocations. Primary significance requires a positive observed difference and p <= 0.025,
as well as complete bidirectional trace-to-request coverage and the integrity gates below. A missing
or unverifiable acknowledgment inventory is not zero and prevents this complete-case primary claim.
No substitute outcome replaces this test after outcomes are inspected.

Significance alone does not identify the intended mechanism. Independently reconstruct accepted
acknowledgment -> next agent action -> command/read/edit result -> continuation chains, preserving
typed request, thread, turn, agent, patch and response identities. Before interpreting excess
handoffs as incremental work, classify their code/evidence into:

- genuinely remaining requested feature work;
- repair of a validation failure in already submitted work;
- review-requested repair or evidence;
- formatting-only repair;
- rejected/resubmitted work, no-op, or unresolved classification.

Classification uses actual saved edits, prior state, command/review evidence and feature requirements,
not patch titles, condition labels, or a presumed number of ideal increments. Retain uncertain labels.
The primary arithmetic includes every delivered successful acknowledgment regardless of label.
It establishes an assignment effect on all handoffs, not specifically substantive increments.

A fixed-sequence secondary test evaluates the count of acknowledgments implementing genuinely
remaining requested feature work. Test it at the same alpha 0.025 only if the primary test passes;
this sequence does not consume an additional family-wise alpha allocation. Every primary ACK must
have exactly one classification record. Mixed or unresolved ACKs receive a finite zero-to-one
indicator interval, never exclusion; repairs with no new requested feature work receive zero.
Use the conservative lower treatment-minus-control contrast and worst-case one-sided randomization
p-value upper bound over those intervals and the same 324 allocations. Both positivity and
p-upper <= 0.025 are required. Classification evidence must be frozen before the helper computes
condition contrasts. Descriptive chains alone cannot establish a causal substantive component when
this secondary test fails or remains classification-ambiguous.

Report exact observable model turns and completed response IDs separately. Join the additional
edit/check/read continuations to actual input-item charges and request-field overhead. Identify
previously read results that are charged again, including their per-response token counts and native
item IDs. One repeatedly charged tool-result item is not repeated tool execution. Report validation
commands and results so naturally required work is distinguishable from unnecessary or malformed work.

The resulting causal claim, if supported, is policy -> different substantive handoff/continuation
behavior, combined with an exact accounting explanation of the responses it entails. It is not a
natural indirect-effect estimate, a unique percentage share, or automatically proof that net
whole-workflow raw tokens increase. Countervailing response/context changes remain visible.

## Token accounting and endpoint relationship

Whole-workflow raw input plus output remains a reported secondary outcome, including cached input,
hidden/title calls, review/fix/linearization, retries and failures. Cached, uncached, output, and
reasoning-subset fields are separate; reasoning is never added twice. Preserve compaction and native
identity audits. Missing usage is not zero. Use the original study's explicit conditional response
inventory assumptions and 1,178,000-token per-missing-response ceiling unless a separately justified,
prospectively frozen narrower bound is available before admission. Do not use observed maxima,
later retained-input charges as original output cost, or midpoint tests.

The primary mediator does not rely on those loose token ceilings. Report any net raw-token contrast
as an accounting interval and call it positive only if its entire interval is positive. Otherwise,
the mediator and exact observed replay charges may establish a specific causal mechanism without
establishing its net raw-token magnitude. Direct prompt byte/token cost and downstream behavioral
effects are not conflated; padding is prohibited.

The historical approximately 50% WL endpoint reduction remains accepted under the user's working
no-quality-loss assumption. This experiment tests a source-grounded cause suggested by the historical
test/edit/check traces. It does not recalculate that endpoint or claim that this one component
explains every saved token. The canonical quality scorer runs offline and all results remain visible;
quality is neither a post-hoc inclusion filter nor a reason to secretly alter the task.

## Instrumentation and integrity gates

Version 2 records exact original and forwarded full prompts plus ordered renderer-owned spans at
existing policy injection, successful acknowledgment and command-result boundaries. Control has the
same logging and unchanged prompt bytes. Actual captured provider requests must match the corresponding
forwarded strings in both directions; non-target strings and known-session raw followups remain
unchanged. Version 1 study sources and trace semantics are independent.

The observer keeps raw response metadata, maximum 1,000 ms usage grace with immediate release on
resumed output (`forward`), and all existing cancellation and forwarding behavior. No grace extension,
extra generation, model setting, or added agent-visible instrumentation is part of this factor.
Stage/busy/idle/outer/grace limits remain 7,200/1,800/300/86,400/20 seconds.

An opt-in observer inventory hashes actual eligible project configuration/rules/hooks layers before
the primary app-server child starts and at the existing Git-checkpoint boundaries. Unsupported
project-root discovery, resource references, symlinks, and invalid activation fail closed. Evidence is
metadata and hashes outside the agent stream, never configuration content or credentials. Snapshot
equality establishes equality at recorded boundaries, not continuous filesystem immutability.

A future-only supervisor classifier may recognize precisely a new trusted-project entry for an
admitted canonical checkout at its prescribed first full-access linearizer start. It must preserve
original raw/parsed/behavioral hashes and the legacy classifier result. Acceptance requires exact
ownership, absent-at-baseline identity, exact `{trust_level: trusted}` value, prior captured prescribed
request and matching typed reply/native permission evidence, unchanged applicable layer inventories,
and equality of the complete remaining parsed configuration. Unknown changes stop new admissions.
An independent offline replay verifies every such verdict from retained evidence. This exception
does not authorize global setting changes or retrospectively clear the initial screen's flag.

Complete parsed-history replay requires the matching external final global configuration; its
contents are not archived. Removing and reinstating only verified owned trust additions must
reconstruct the baseline and every original parsed snapshot hash. A parsed notice-bookkeeping
change retains its original `known_bookkeeping_only` label but fails this future admission gate
with `parsed-bookkeeping-history-not-replayable`: neither broad normalization nor a stored success
boolean substitutes for the exact replay. Formatting-only changes with identical parsed content
retain their ordinary classification. The helper executes from the exact source bytes whose hash
is frozen; the loaded hash, current source hash and phase manifest pin must agree.

Native permission-context publication is asynchronous. If, and only if, the exact new owned key,
full configuration remainder, original/forwarded prescribed full-access request, accepted typed
reply, thread-start identity/time and unchanged pre-spawn/pre-linearize/current project layers are
already verified, an absent or incomplete native attestation may enter an explicitly unverified
pending state. Pending holds new admissions, leaves active workflows untouched and has a fixed
30-second deadline from the first-seen configuration snapshot. Wrong or malformed permissions,
unmatched/pre-start trust, unrelated configuration differences or other missing core evidence are
not pending exceptions. They remain integrity failures.

Resolution is a later journal event with its own cutoff and native proof, never a claim that the
original snapshot was already verified. Offline replay checks the initial core evidence prefix,
later native attestation and deadline separately. Original pending records retain their
`allows_admission: false` status. An unresolved deadline or contradictory evidence sets the
persistent unexplained-drift stop condition. This changes only future admission gating, not an
agent prompt, request, response wait or interruption policy.

Before admission, required format, all-target/all-feature clippy, and all-target/all-feature tests
pass for affected crates. New tests run RED before implementation; committed tests remain unchanged.
Default/control identity, v1 compatibility, v2 multi-span integrity, malformed activation and error
propagation are covered. Bounded real configured-agent verification exercises actual policy delivery,
accepted edits, unchanged-cardinality acknowledgments, remaining work and completion. Diagnostics are
recorded separately and cannot count as observations. Freeze actual binaries, source inputs,
lockfiles, drivers, wrappers, helpers, protocols and allocation before launching the phase.

## Reporting and progression

Report all twelve slots, exact allocation/test support, intervention integrity, mediator counts,
remaining-work versus repair chains, repeated-input identities, token-accounting intervals, resource
incidents and offline quality facts. Shared CPU/I/O/subscription capacity may create interference;
separate checkouts and mixed-wave randomization do not by themselves prove absence of interference.

A positive mechanistic result must connect the delivered policy to actual meaningful work-unit
behavior and response-input replay. A null or failed integrity result remains retained and does not
authorize repetition until favorable. Further work uses a separately frozen hypothesis, factor,
observation count and remaining multiplicity allocation. Completion of this phase is distinct from
completion of the user's broader exact-mechanism investigation. Under shared-capacity interference,
the randomized result concerns the specified mixed-wave allocation regime. A sharp-null test of no
assignment effects does not decompose isolated per-workflow treatment effects from spillovers.
