# Repeated compaction metadata accounting supplement

`accounting_compaction_carry.py` is a separately pinned offline sibling of the immutable pre-turn context helper. Its only accounting extension is provenance for repeated, unusable compaction `last` metadata. It never creates response usage, changes the original cumulative arithmetic, alters strict accounting limits, clears missing-response gaps or changes Work Leaf/provider behavior.

The module has no command-line execution or provider operation. Its `audit_run(entry, frozen, sessions_root)` callable is reserved for a separately declared numerical scope after review. Implementation qualification uses only synthetic fixtures and the unchanged offline regression suites; the original candidate001 and corrected-nine reports remain unknown/unchanged.

## Carry ownership and invalidation

An origin is established only inside the unchanged successful branch for one explicitly named native/raw compaction response, its matching complete public lifecycle, and an unchanged cumulative omission. A carry warning requires:

1. The same capture and thread, with a later exactly accepted local turn.
2. A position after that origin's complete lifecycle.
3. Exact typed equality of the full `last` and cumulative objects, not a match on selected fields or shape alone.
4. Cumulative usage equal to both the preceding cumulative value and the independently maintained raw-prefix-minus-named-omission expectation.
5. No intervening new same-thread response, new compaction, changed metadata values or unsupported ownership lifecycle.

An exact duplicate raw response ID is not a new response. A distinct response invalidates carry even when its explicit measured usage is zero. A new compaction must prove its own origin; the old omission cannot be charged again. Other-thread events do not transfer the origin.

Unsupported `thread/*` or `turn/*` lifecycle notifications invalidate the identified thread's origin; unresolved/conflicting ownership clears carry state. The known metadata/status and turn-start/completion notifications preserve it. Ordinary generated item and tool activity remains in the stream: it does not prove absent generation or a bounded response tail. The module makes no general provider-semantics claim for unknown notification families.

## Warnings, tails and retained failures

Every carry is emitted as `unusable_compaction_last_metadata_carry_forward`, with the originating response/item/turn, exact origin and current physical server lines, lifecycle boundaries and typed-value hashes. It has `establishes_completed_response_usage=false` and `used_for_fresh_usage_or_tail_recovery=false`.

Both original and carried warnings enter the existing proof-view warning set **and** the affected-turn set. The unchanged conservative branch sets every affected interrupted gap's `response_count_upper=None` and `proof=None`; affected turns are excluded from late-terminal usage recovery. All five generated-but-unmeasured synthetic interrupted continuations retain unbounded upper endpoints when passed to the unchanged strict accountant.

`instrument_original` retains original pure reconciliation errors separately from derived errors. It does not execute a second original whole-workflow audit. Each capture's client/server/grace row hashes are checked against the exact retained source files, including physical blank-line offsets, before assigning a capture path.

The original outer-scope diagnostic applies only the frozen pre-cumulative identity guards and explicitly records that it is not a second full original audit. It requires a complete capture census. If an earlier retained failure stopped capture reconciliation, the diagnostic is `unavailable_partial_capture_census` with no claimed whole-scope error. Existing original reports remain authoritative for their complete original outcomes; the diagnostic neither overwrites them nor invents an old total.

## Complexity and qualification

The added carry state is one forward pass with one origin per thread. Original and derived pure reconciliation are each evaluated once per capture for separate diagnostics. Native inventory hashing occurs once per workflow, not once per capture; capture source and row hashing are linear in bytes. Sorting thread/capture identities costs O(T log T + C log C). No introduced per-event history scan or O(E²) loop exists. The predecessor's already documented per-native-thread dependency compilation term remains O(T × D) for fixed dependency bytes D.

The source/test gate receipt is [CARRY-VALIDATION.json](CARRY-VALIDATION.json). It records RED-first reproduction, 26 new tests, 72 unchanged predecessor tests and the repository's Rust gates. Existing committed test sources are not modified; the frozen accounting reconciliation tests run against the derived callable in memory.

No real-agent workflow is affected: this is analysis-only code over already retained records. Provider verification is therefore not applicable, and no provider was launched. Saved-workflow reconciliation/total replay remains a separate explicitly authorized action; no successful total or resolved tail is claimed by these implementation checks.
